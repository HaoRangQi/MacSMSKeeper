# 排查指南

## 诊断日志

默认**关闭**。打开方式：「设置与诊断 › 诊断日志」。

打开后重现一次问题，然后点「在访达中显示」，把日志文件发给开发者。
日志按天分文件：`~/Library/Logs/SMSKeeper/smskeeper-YYYY-MM-DD.log`。

### 日志记录什么

操作步骤、错误信息、SQLite 错误码、条数、耗时、表名、SQL 模板、备份文件名。

### 日志绝不记录什么

**短信正文、验证码、发件人号码、guid 内容、附件数据。**

这不是承诺，是代码里强制执行的：`Sources/Core/Logger.swift` 内置字段黑名单
（`text` / `body` / `sender` / `guid` / `content` / `handle` / `code` …），
命中黑名单的字段一律替换为 `[按隐私策略省略]`，超长值截断到 160 字符。
即使将来有人误传，也落不到磁盘上。

日志只在本地，不联网上传。

## 已知问题与修复

### `no such function: xxx`

**现象**：点删除或还原后弹窗「数据库错误：no such function: xxx」，
xxx 可能是 `after_delete_message_plugin`、`before_delete_attachment_path`
等你没见过的名字。

**原因**：macOS 的「信息」App 打开 `chat.db` 时，会用 `sqlite3_create_function`
注册一批私有 SQL 函数；库里的触发器在增删消息时调用它们。我们的程序自己打开
数据库，连接上没有这些函数，写操作就失败了。用 `sqlite3` 命令行直接删也会报
同样的错——这不是本工具的问题，是 chat.db 的结构决定的。

**修复**：写连接建立时，扫描 `sqlite_master` 里全部触发器，把其中调用的函数名
逐个探测（`SELECT name()`），SQLite 里不存在的才注册成空实现。内置函数会被探测
识别、绝不覆盖。触发器因此能正常走完。删除前仍会退出「信息」App 并做整库备份，
所以跳过这些私有函数是安全的。

这个方案不依赖命名规律——`*_plugin`、`before_delete_*`、乃至完全没见过的名字
都能覆盖，系统升级后新增函数也不用改代码。

**理论上**：如果 macOS 把函数调用藏在触发器以外的地方（视图、CHECK 约束、
生成的列），扫描会漏掉。真遇到就把日志发来，那是新情况。

### 删了短信，但「信息」App 列表里还剩一个空对话

**原因**：只删 `message` 表不够。`chat` 表里的会话记录不删，「信息」App
的列表里就留一个点进去空白的对话（搜索那个号码还能搜到）。

**修复**：删除消息后，会检查本次涉及的每个会话是否还有消息，
没有就连带清掉 `chat`、`chat_handle_join` 等关联行。
被清掉的会话整行会存进回收站，还原时写回，所以还原后会话会回来。

自检里有专项用例：构造一个只关联一条消息的会话，删掉那条消息后
验证会话被清除、还原后会话恢复，同时确认有消息的会话不受影响。

### `database is locked`

「信息」App 没有完全退出。删除前程序会自动请求它退出；如果失败会中止操作。
手动 ⌘Q 退出「信息」后重试。

### 提示未授权 / 读不到短信

见 [permissions.md](permissions.md)。注意：授权后必须**完全退出**本 App 再打开，
只关窗口不算退出。

## 出问题时请提供

1. 日志文件（`~/Library/Logs/SMSKeeper/` 下当天那个）
2. 弹窗的完整文字
3. macOS 版本（「关于本机」）
4. 当时在做什么操作（点了哪个清理规则 / 删了多少条）

日志里已有条数、错误码和 SQL 错误原文，通常足够定位。
